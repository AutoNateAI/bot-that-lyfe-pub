Garbage In

A vague prompt gets the most average answer. A trusted answer gets you a confident mistake.

  • What a language model actually does: predict the next token, over and over
  • The two opposite failures: asking too little, trusting too much
  • How to name what went wrong instead of blaming the tool

edit_note Activity · The four-word autopsy
  1. Find a prompt you sent an AI tool this week that disappointed you.
  2. Rewrite it with: the exact file or input, the exact problem, one thing it must not touch, and what the finished output looks like.
  3. Run both. Write two sentences on what changed — and what the first answer was 'averaging' toward.

Journal this

In <file>, <function> breaks when <specific case>.
Fix only that. Don't touch <area>.
Show me <the changed function / a diff / a one-line note>.

Talk about it

  • Did I say which part?
  • Did I say what not to touch?
  • Do I know exactly what it changed?
  • Did I check the answer against the source?

Episode 2

The Room, Not Just the Ask

A model can only work with what's in its context window. Too little and it guesses; too much and it drowns.

  • What the context window is — and what fills it without you noticing
  • Why flooding it backfires ('lost in the middle')
  • Four context-engineering moves and a project context file
play_circle Watch menu_book Give It the Room, Not Just the Askmenu_book Feeding It the Right Files
edit_note Activity · Build the room
  1. Pick a real bug or task. List every file/document you'd normally paste in.
  2. Cross out everything the task doesn't touch. Summarize anything longer than a page into its decisions.
  3. Start the session with: 'Before you change anything: what files can you see, and what are you assuming?'
  4. Write a 6-line project context file (AGENTS.md / CLAUDE.md) with the rules you keep repeating.

Journal this

# Project context
- Runtime + versions, and "no new dependencies without asking"
- Where the important logic lives (and what not to duplicate)
- House rules (never delete TODOs, tests before refactors)
- Files to ask before touching

Talk about it

  • Did I give it only what the task touches?
  • Did I summarize instead of paste?
  • Did I ask what it can see before it acted?
  • Is the context written down once, not re-explained daily?

Episode 3

Role, Task, Constraints, Format

A prompt is a scope of work. Four lines turn a wish into a spec — and you decide what done looks like before you start.

  • The four-row prompt: Role, Task, Constraints, Format (+ Done)
  • Why a role works like priming
  • Treat the first answer as a draft, not a verdict
play_circle Watch menu_book Structuring the Ask
edit_note Activity · Scope it like a contract
  1. Take a real message you need to write (a follow-up, a bug report, a cover letter).
  2. Write the four rows. Then add DONE: three checkable criteria.
  3. Generate, then do one revision pass that cuts something and adds one specific detail.
  4. Check the result against DONE. If it fails, fix the prompt, not just the output.

Journal this

ROLE: <who is speaking, to whom>
TASK: <one job, named>
CONSTRAINTS: <length · tone · must include · must avoid>
FORMAT: <the shape of the answer>
DONE: <3 checkable criteria>

Talk about it

  • Is the role a lens or a compliment?
  • Is there exactly one task?
  • Could someone else check DONE without asking me?

Episode 4

That's Not a Source

Fluent isn't factual. A sentence isn't a source — check what would hurt if it were wrong.

  • Why models produce plausible fabrications (and why people do too)
  • The ten-second verification kit
  • Package hallucinations and slopsquatting — the security risk
  • Closing ambiguity before the model closes it for you
play_circle Watch menu_book When It Gets It Wrong
edit_note Activity · Catch one in the wild
  1. Ask an AI tool for code that uses a library you've never used.
  2. Before running anything: `npm view <package>` (or pip index / docs) for every import, and check every method it calls exists.
  3. Rewrite the prompt to close two ambiguities (e.g., dedupe key, keep first vs last) and compare.

Journal this

npm view <package> name        # does it exist?
node -p "typeof [].someMethod" # does the method exist?
# read the official docs · run it on a tiny real input

Talk about it

  • Does every package and method actually exist?
  • Did I close the ambiguities that matter?
  • Am I verifying what would hurt — not arithmetic?

Episode 5

The Missing Ledger

Memory is a storyteller; a database is a witness. Model the truth once, then ask it precise questions.

  • File vs. in-memory object vs. database — three different deals
  • Tables, primary keys, foreign keys: one row per truth
  • SELECT, WHERE, JOIN — and the JOIN that silently inflates COUNT
  • Querying from code so the answer is the same every time
play_circle Watch menu_book The Missing Ledgermenu_book The Blueprintmenu_book Talking to the Data
edit_note Activity · Build the ledger
  1. Create people, ideas and feedback tables in SQLite (feedback points at both with foreign keys).
  2. Insert 5 people (one duplicate under two spellings), 3 ideas, 8 feedback rows (one person comments 3 times).
  3. Count 'people who gave feedback on idea 3' with COUNT() after a JOIN, then with COUNT(DISTINCT person_id). Explain the difference in one sentence.

Journal this

SELECT COUNT(DISTINCT person_id) AS people
FROM feedback
WHERE idea_id = 3;

Talk about it

  • Does each real-world thing exist exactly once?
  • Am I counting rows or the things I actually mean?
  • Is the question answered by code, not by memory?

Episode 6

The Web Under the Table

When relationships repeat, loop, and carry their own facts, they're a graph. The connections are the knowledge — for brains, neural nets, and your AI's context.

  • The tell that a table should be a graph
  • Nodes, directed edges, hops, cycles — and traversal with WITH RECURSIVE
  • Feeding a graph path to an AI as context, with sources
play_circle Watch menu_book The Web Under the Tablemenu_book The Scoreboard Comes Alive
edit_note Activity · Shortest way in
  1. Add an introductions table (from_name, to_name, venue, date) with at least one person introduced twice and one cycle.
  2. Write the WITH RECURSIVE query that finds the shortest path from you to a target, without walking in circles.
  3. Give an AI only that path plus the source rows and ask it to draft an intro request. Compare with giving it the whole table.

Journal this

WITH RECURSIVE path(person, hops, route) AS (
  SELECT 'Nia', 0, 'Nia'
  UNION ALL
  SELECT i.to_name, p.hops + 1, p.route || ' → ' || i.to_name
  FROM introductions i JOIN path p ON i.from_name = p.person
  WHERE p.hops < 4 AND instr(p.route, i.to_name) = 0
)
SELECT route FROM path WHERE person = 'Fairview Parks'
ORDER BY hops LIMIT 1;

Talk about it

  • Does this relationship have facts of its own? → its own table
  • Can my traversal loop forever? → stop on revisits
  • Am I giving the AI the path, or the haystack?
